Last updated: 2026-09-20 11:33 IST (UTC+05:30)

## Product goal

Build a premium, accurate, easy-to-use **CPC Digital Catalogue** that helps customers discover, browse, search and understand Cambridge Publishing Company publications.

**The catalogue is the primary product.** Selection, custom kits and Submit Request are secondary convenience features. This is not an e-commerce/order-management system, and request workflow must not drive the catalogue architecture.

Primary journey:

`Discover/Browse/Search → Category → Class/Stage → Publications → Book Details`

Optional continuation:

`Select publications → Review Selection → Submit Request`

## Catalogue data model — current state

Canonical schema migration is complete in source and the previously broken Kit Builder was live-tested successfully by the user on 2026-08-16.

- `class` is now the single Nursery–Class 10 classification field.
- `class` is always an array.
- legacy catalogue `levels` records were removed from `catalogue-data.js`.
- Early Learning common titles explicitly use `["Nursery", "LKG", "UKG"]` to preserve the previous availability behaviour.
- Draw & Colour A/B/C map respectively to Nursery/LKG/UKG.
- all current school textbook records are explicitly English medium, including Kannada/Hindi language subjects.
- current exam/guide records use English/Kannada medium only; legacy Hindi-medium values were removed.
- `catalogue-query.js` queries class arrays without legacy level compatibility.
- `catalogue-validator.js` validates the canonical array model and rejects a legacy `levels` field.
- Kit Builder and Book Details work with class arrays.
- School Books and Exam Preparation use the shared canonical class-aware query layer.
- request submission flattens class arrays safely for the current backend snapshot fields.

Current catalogue record count remains structurally equivalent to the prior source: 150 records are generated by the canonical source definitions.

`js/catalogue-data.js` is the current catalogue source, but it should not be assumed to be the permanent authoritative product master. The next architecture phase is to design a maintainable catalogue-first Product/Publication Master and validate it against real CPC item data before database implementation.

## Current architecture priority

**IMMEDIATE NEXT: design the canonical CPC Product/Publication Master schema using verified/sample CPC item data. Do not implement a Supabase product migration until the schema has been validated against real catalogue cases.**

The schema must be catalogue-first and support, as required by actual CPC data:

- publication/product identity
- title and series
- Early Learning / School class or College stage / Competitive Exam classification
- subject
- medium
- book type
- edition / academic year / revision lifecycle
- ISBN and MRP
- cover and catalogue media
- descriptions/features
- sample pages and digital resources where applicable
- active/discontinued catalogue state
- search/filter/sort metadata
- internal SKU/Tally/ERP mapping kept separate from public catalogue presentation

Selection/request tables reference catalogue publications; they do not define the publication schema.

## Important recovered decisions

- The Digital Catalogue is the primary product; Selection/Submit Request is an add-on.
- Do not architect this as an e-commerce/order-management application.
- Do not maintain both `level` and `class` for Nursery–Class 10.
- Use **`class` only** in catalogue product data.
- `class` supports multiple applicable classes via an array.
- Early Learning school-stage values are Nursery, LKG and UKG. Playgroup still requires real product-data confirmation.
- School values are 1–10.
- College uses a separate academic `stage` concept such as 1st PUC, 2nd PUC and Degree.
- Subject and medium are separate concepts.
- A Kannada subject book is **not** automatically Kannada medium.
- Regular textbooks are English medium.
- Kannada-medium editions are used only where an actual Kannada-medium publication exists.
- Do not infer medium from subject.
- Do not invent catalogue/product data to fill empty UI.

## Navigation/UX rules already learned

- Internal catalogue pages should expose a compact direct Home route plus the contextual parent/back route where practical.
- Back navigation on internal/section pages should be consistently placed at the top-left of the content area; do not center the Back control just because the hero content is centered.
- Preserve browser-native Back/scroll restoration for ordinary View Book navigation.
- Do not persist stale scroll positions and replay them on refresh/revisit.
- My Selection is shared across catalogue sections.
- Preserve working Review Request UI/backend while catalogue architecture is developed.
