# CPC Digital Catalogue — Supabase Catalogue Architecture V1

Last updated: 2026-09-20 15:53 IST (UTC+05:30)

## Purpose

This document defines the first database architecture for the **catalogue itself**. The Digital Catalogue is the primary product; Selection and Submit Request remain secondary convenience features.

This is an architecture specification only. Do not replace the live `js/catalogue-data.js` source until the pilot dataset has been imported and verified against the existing catalogue journeys.

## Design principles

1. One verified CPC publication/sellable item is one canonical publication record.
2. Keep the model lean. Do not create lookup tables for every text attribute unless a real relationship/management need appears.
3. Preserve CPC's official customer-facing title; normalized metadata exists for discovery/filtering and does not reconstruct the title.
4. Series, subject, medium and book type are independent concepts.
5. Medium is optional and is used only where CPC genuinely distinguishes medium-specific publications (not as a blanket attribute for ordinary textbooks).
6. Category is excluded from V1. Discovery groupings should be derived from section, series, class/stage, subject and book type unless later evidence proves a separate category is needed.
7. Internal Tally/ERP terminology remains separate from the public catalogue.
8. Do not invent missing publication data.

## Canonical publication table

Proposed table: `publications`

| Column | Type | Rule / meaning |
| --- | --- | --- |
| `id` | uuid | Primary key; generated by database; immutable internal identity |
| `catalogue_section` | text | Required controlled value |
| `series` | text | Nullable; only a genuine CPC publication family/series |
| `title` | text | Required official/customer-facing publication title |
| `class_stage` | text[] | Required array; empty array means intentionally not class/stage restricted |
| `subject` | text | Nullable normalized subject, e.g. `Science` for a publication titled `Vignana` |
| `medium` | text | Nullable; currently `English` or `Kannada` where applicable |
| `language_position` | text | Nullable; `First Language`, `Second Language`, `Third Language` |
| `book_type` | text | Required controlled generic publication type |
| `mrp` | numeric(10,2) | Nullable; non-negative |
| `isbn` | text | Nullable; retain hyphenated display form; normalized uniqueness can be validated during import |
| `author` | text | Nullable; V1 mirrors the clean master rather than introducing contributor tables prematurely |
| `co_author` | text | Nullable |
| `pages` | integer | Nullable; positive when present |
| `length_cm` | numeric(8,2) | Nullable; positive when present |
| `breadth_cm` | numeric(8,2) | Nullable; positive when present |
| `thickness_cm` | numeric(8,2) | Nullable; non-negative when present |
| `weight_kg` | numeric(8,3) | Nullable; non-negative when present |
| `status` | text | Required; default `Active` |
| `description` | text | Nullable catalogue copy; not required in Excel pilot |
| `features` | text[] | Nullable catalogue feature bullets; not required in Excel pilot |
| `sort_order` | integer | Nullable manual display override |
| `featured` | boolean | Default false |
| `new_release` | boolean | Default false |
| `created_at` | timestamptz | Default now() |
| `updated_at` | timestamptz | Default now() |

### Why UUID + optional SKU

Database identity and CPC business identifiers are different concerns. `publications.id` is generated and immutable. CPC does not need to invent SKU values merely to satisfy the database.

The current Excel `SKU ID` remains optional business data and should flow to `product_mappings.sku`, not become the publication primary key.

## Controlled V1 values

### Catalogue section

- `Early Learning`
- `School Learning`
- `College and University`
- `Competitive Exams`

### Book type

Initial controlled vocabulary validated against the pilot data:

- `Textbook`
- `Reader`
- `Semester Book`
- `Workbook`
- `Writing Book`
- `Activity Book`
- `Drawing Book`
- `Rhymes Book`
- `Guide`
- `Combined Guide`
- `Question Bank`
- `Assessment Book`

Add a value only when a verified CPC publication cannot reasonably fit the existing vocabulary.

### Medium

- `English`
- `Kannada`
- null when medium classification does not apply

Do not infer medium from subject. Ordinary textbooks/readers/workbooks do not receive `English` merely because their content is English.

### Language position

- `First Language`
- `Second Language`
- `Third Language`
- null when not applicable

Combined-guide shorthand such as `Combined K-I (EM)` remains in the official title in V1. Do not add a catalogue-wide `language` field until a real filtering/discovery requirement needs it.

### Status

Initial values:

- `Active`
- `Discontinued`
- `Out of Print`
- `Archived`

Pilot imports may default blank status to `Active` only for rows explicitly approved as current catalogue data.

## Class / stage semantics

`class_stage` is an array even though the current clean Excel pilot has one Class/Stage cell per row.

Examples:

```text
["LKG"]
["2"]
["10"]
["2nd PUC"]
["5", "6", "7"]
[]
```

An empty array means the publication is intentionally not restricted to one class/stage within its catalogue section, e.g. a generally applicable Early Learning activity title.

Do not use `NULL` for this semantic. Import validation should distinguish an intentional empty array from an unresolved/missing classification before data is accepted.

## Public catalogue vs internal mapping

The existing `product_mappings` table remains the internal operational bridge.

Target relationship:

```text
publications.id
    ↓
product_mappings.product_id
    ├── sku
    ├── isbn (internal/reference copy where useful)
    ├── tally_item_name
    ├── tally_stock_item_id
    └── erp_item_id
```

`product_mappings.product_id` is currently text because it predates the catalogue database. During implementation, migrate it safely to reference the canonical publication identity or add a compatible UUID reference without breaking the working request add-on.

Do not expose Tally/ERP fields through the public catalogue read model.

ISBN is public publication metadata and belongs on `publications`; the mapping layer may retain an ISBN snapshot/reference for fulfilment compatibility during migration.

## Publication assets

Proposed table: `publication_assets`

| Column | Type | Meaning |
| --- | --- | --- |
| `id` | uuid | Primary key |
| `publication_id` | uuid | FK to `publications.id` |
| `asset_type` | text | `cover`, `back_cover`, `sample_pdf`, `digital_resource`, future verified types |
| `storage_path` | text | Supabase Storage path or migration-safe asset path |
| `external_url` | text | Nullable; for verified external digital resources |
| `label` | text | Nullable customer-facing label |
| `sort_order` | integer | Default 0 |
| `active` | boolean | Default true |
| `created_at` | timestamptz | Default now() |

### Asset migration rule

Do not move all existing GitHub cover files to Supabase Storage in the first step. The pilot may continue to reference current cover paths while the database source is validated. Storage migration is a separate controlled phase.

## Public read model

The browser should not query internal mapping/request tables.

Create a public catalogue read surface (view or narrowly permissioned table access) containing only customer-safe catalogue fields, for example:

- publication id
- section
- series
- title
- class/stage
- subject
- medium
- language position
- book type
- MRP
- ISBN
- description/features
- display flags
- public asset references

Only `Active` publications should appear in the normal public catalogue unless an explicit preview/admin mode is introduced later.

## RLS / security direction

- Enable RLS on catalogue tables.
- Public/anon role: read-only access to the approved public catalogue read surface.
- Public/anon role: no write access to catalogue master tables.
- Internal mapping/request tables remain private as currently designed.
- Catalogue management writes will later require authenticated staff/admin roles; do not open writes merely to simplify initial data loading.

## Search / indexes

Initial indexes should support the actual discovery paths rather than speculative analytics:

- `catalogue_section`
- `series`
- `subject`
- `book_type`
- `medium`
- `status`
- GIN index on `class_stage`

Add text-search/trigram indexes for title/series/subject only when the Supabase-backed universal search is implemented and measured.

## Pilot import strategy

1. Keep live `js/catalogue-data.js` unchanged as production source.
2. Create catalogue tables through a versioned migration.
3. Import the curated ~30-row Publication Master pilot dataset.
4. Validate controlled values, intentional blanks, ISBN/MRP types and class-stage arrays.
5. Map pilot rows to existing cover assets without requiring an immediate Storage migration.
6. Build a data adapter/query layer that can read Supabase records into the existing catalogue UI contract.
7. Test representative journeys: Early Learning, class-independent title, School textbook, individual guide, combined guide, LBA English/Kannada medium, PUC.
8. Test Browse/Search filters and Book Details against the pilot.
9. Compare results with the current static catalogue and fix model/query issues.
10. Only after verification, plan bulk master-data migration and eventual retirement of `catalogue-data.js` as the authoritative source.

## Existing request add-on compatibility

The current request system is already working and should remain stable during catalogue migration.

Current request tables use text `product_id` snapshots and server-side `product_mappings`. Do not redesign request workflow as part of the catalogue pilot. Adapt the bridge only when canonical publication IDs are ready, preserving historical request snapshots.

## Explicitly deferred from V1

- separate lookup tables for series/subject/book type/medium
- edition/publication-family hierarchy
- contributor/author relationship tables
- live ERP inventory
- order management
- staff request workflow expansion
- catalogue-wide `language` field
- Category field
- full cover migration to Supabase Storage
- customer accounts/e-commerce

These can be introduced later when real requirements justify them.
